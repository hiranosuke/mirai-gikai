# みらい議会＠さいたま市 PoC 運用案

作成日: 2026-06-13

## 0. このドキュメントの位置づけ

「みらい議会」のコードベースを使って、**さいたま市議会版を個人で立ち上げ・運用できるか**を試す
PoC（Proof of Concept）の運用計画と判断基準をまとめる。

- **運用主体**: 個人（1人）
- **コスト**: 自費（AI 利用料・インフラ費）
- **検証したいこと**: 「個人が、自費・自力で現実的に回せるか」
  - コスト面: 1議案・1インタビューあたりいくらかかるか / 月次でいくらに収まるか
  - 労力面: 1議案を公開可能な状態にするのに何時間かかるか / 定例会1サイクルを回せるか

議事録（discusscabinet.net / さいたま市議会会議録）との技術連携は**別途検討**とし、
本 PoC では「議案コンテンツは人手 + AI 補助で用意する」前提で進める。

## 1. PoC の成功 / 失敗を判断する基準

数字は仮置き。**実測値で更新する**（実測は §4 の Grafana ダッシュボードで取得）。

| 観点 | 指標 | 暫定の合格ライン | 計測元 |
|---|---|---|---|
| コスト | インタビュー1完了あたり LLM コスト | ≤ 数十円 | `chat_usage_events.cost_usd` |
| コスト | 月次 LLM コスト合計 | 自費で許容できる上限内（例: 月数千円） | `chat_usage_events` |
| 労力 | 1議案を公開状態にする作業時間 | ≤ 1〜2 時間 | 手動記録（§5） |
| 労力 | 1定例会サイクル（議案選定〜論点公開）を回しきれるか | 回しきれる | 運用ログ |
| 価値 | インタビュー完了率 | 着手者の過半数が完了 | `interview_sessions` |
| 価値 | 議案あたり収集意見数・論点数 | 論点が複数立つ | トピック分析テーブル |

「コストが許容外」「1議案に半日かかる」「誰も完了しない」のいずれかなら、
スコープ縮小（議案本数を減らす / インタビューを簡素化する）か撤退を判断する。

## 2. 運用サイクル（定例会ベース）

さいたま市議会の定例会は通常 年4回（2月・6月・9月・12月）。これを運用の単位にする。

1定例会あたりの流れ（想定 2〜3 週間）:

1. **議案選定**（開会前後）: 市民の関心が高い / 生活影響が大きい議案を 3〜5 本ピック
2. **コンテンツ作成**（Admin）: 議案書・議事録をもとに `bill_contents` の簡易（standard）/
   詳細（advanced）を作成。AI で下書きし、**必ず人間が原文と突合してから公開**する
3. **インタビュー設定**（Admin）: `interview_configs` でテーマ・事前質問を設定
   （`/api/interview-config/generate` の AI 生成を下書きに使う）
4. **公開・告知**: 公開 → SNS 等で告知
5. **意見収集**（採決まで）: 市民が AI インタビューに参加 → レポート生成
6. **論点可視化**: トピック分析（Phase1〜3）を実行し `/bills/[id]/opinions` で公開
7. **振り返り**: 採決結果と市民意見を比較。本サイクルのコスト・労力を記録（§5）

PoC では最初の 1 サイクルを**議案 1〜2 本**に絞って回し、コスト・労力の実測を取る。

## 3. 既存機能の転用方針（PoC スコープ）

国会前提の作りを「そのまま使う / 読み替える / 後で作り替える」で仕分け。
PoC 第1弾では**大改修をせず**、計測と運用ログの土台づくりを優先する。

| 機能 | 方針 | 備考 |
|---|---|---|
| `bills` / `bill_contents`（難易度別） | そのまま | 市議会議案に流用 |
| AI インタビュー（中核） | そのまま | 生活直結テーマと好相性 |
| トピック分析（論点可視化） | そのまま | 市民意見の論点集約 |
| モデレーション | そのまま（必須） | 公開プラットフォームのため |
| `chat_usage_events`（コスト記録） | そのまま | **PoC のコスト計測の生命線** |
| `diet_sessions`（国会会期） | 読み替え（増分2） | さいたま市議会の定例会/臨時会へ |
| `mirai_stances`（チームみらいのスタンス） | 作り替え/停止（増分2） | 該当議員不在なら「論点整理」へ転用 or 非表示 |
| `originating_house`（衆/参） | 不使用（増分2） | 市議会は一院制 |
| `kokkai/[slug]` ルート | 改名（増分2） | 「定例会」ページへ |
| 利用規約 / プライバシー / トップコピー | 差し替え（増分2） | さいたま市版へ |

## 4. 計測: Grafana ダッシュボード（増分1・本 PR で作成）

PoC の主目的「コスト・労力で回るか」を**継続的に可視化**するため、
ローカル Supabase の Postgres を直接読む Grafana スタックを `observability/` に用意する。

- 構成: `observability/docker-compose.yml`（Grafana）+ プロビジョニング（datasource / dashboard）
- 接続先: ローカル Supabase Postgres（`host.docker.internal:54432` / `config.toml` の `db.port`）
- 起動: `cd observability && docker compose up -d` → http://localhost:3002 （初期 admin/admin）
- 詳細手順: `observability/README.md`

初期ダッシュボード `poc-overview` のパネル:

- **累計 AI コスト / 当月 AI コスト**（`chat_usage_events.cost_usd`）
- **日次 AI コスト** 推移、**モデル別コスト**
- **日次トークン消費**（`total_tokens`）
- **インタビュー開始数 / 完了数 / 完了率**（`interview_sessions`）
- **日次セッション**（開始 vs 完了）
- **スタンス分布**（for / against / neutral, `interview_report`）
- **公開レポート数**（`is_public_by_admin`）
- **運用負荷プロキシ**: 公開議案数の推移 / インタビュー設定作成数

> 注: 運用開始前はデータが空。実際に議案を公開しインタビューを回すとパネルが埋まる。
> これが「実測でコスト・労力を判断する」ための計器盤になる。

### Grafana を「逐次」育てる方針

PoC を回す中で見たくなった指標を、ダッシュボード JSON にパネル追加していく。
新しい集計が重い場合は Supabase 側に SQL function / view を追加し、Grafana から呼ぶ。

## 5. 労力（自分の作業時間）の記録方法

LLM コストは `chat_usage_events` で自動的に貯まるが、**人間の作業時間は自動記録されない**。
PoC 中は最低限、手動で運用ログを残す（スプレッドシート or 後述の簡易テーブル）。

記録項目（議案単位）:

- 議案選定にかけた時間
- コンテンツ作成（簡易/詳細）にかけた時間
- インタビュー設定にかけた時間
- レビュー・公開にかけた時間
- 詰まったポイント（ボトルネック）

増分の候補として、運用ログ用テーブル（例: `ops_activity_log`）を追加し
Grafana で「議案あたり作業時間」を可視化することも検討する（本 PR では未実装）。

## 6. 段階ロードマップ

- **増分1（本 PR）**: 計測レイヤー（Grafana スタック）+ 本運用案ドキュメント。
  アプリ本体は変更しない（低リスク）。
- **増分2**: さいたま市向けシード（定例会・サンプル議案・インタビュー設定）+ 用語/ルート/コピーの
  さいたま市版への読み替え。`mirai_stances` の扱いを決定。
- **増分3**: 議事録 → 議案コンテンツの供給フロー（半自動化）。別途検討。

## 7. 運用上の留意点

- **中立性**: 特定会派・候補に有利な見せ方を避ける。論点整理は賛成論拠/反対論拠を併記。
  選挙期間中はトーン・期間に配慮（公職選挙法）。
- **個人情報**: インタビューで市民が個人事情を書きうる。情報開示ページと公開制御
  （`is_public_by_user` / `is_public_by_admin`）をさいたま市版の文言で整備（増分2）。
- **誤情報リスク**: AI 生成の議案要約は誤読の危険。公開前の人手突合を運用フローに固定。
- **コスト暴走防止**: チャットのコストガード（日次/月次上限）を有効化し、Grafana で監視。
- **持続性**: 作業はサイクルに集中する。テンプレ化と AI 下書きで省力化。続かなければ本数を絞る。
